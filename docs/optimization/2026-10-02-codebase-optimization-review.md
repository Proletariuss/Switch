# Switch 整体源码优化方案（2026-10-02）

## 本方案回答的问题

本方案只评估 Switch 源码中的正确性、运行负担、并发边界、可维护性和测试策略，不把文档校对、DMG、缓存清理或视觉重设计算作代码优化。只在可复现的用户收益超过实施与回归成本时改生产代码。

`6982` 已由用户明确永久排除：不研究、不测试、不修改其下载/认证路径。通用 eSIM 其他行为只作回归保护，不借本方案重开该问题。本文是源码审查与建议，不是已实施或真机验证报告。

## 源码基线与已知证据

统计范围为 `app/Sources`、`rust/crates`、`backend/cmd` 与 `backend/internal` 中的一方 Swift/Rust/Go 源码；不含第三方目录与构建产物。Rust 行数包含同文件内的测试。

| 代码区 | 文件数 | 行数 | 说明 |
| --- | ---: | ---: | --- |
| Swift 应用 | 74 | 25,175 | Store、SwiftUI 页面、进程管理与网络/API 客户端 |
| Rust | 111 | 45,591 | 网关、持久化、短信与 IMS/VoWiFi 协议实现 |
| Go 一方生产代码 | 206 | 59,653 | 硬件、eSIM、呼叫、短信、VoWiFi 与兼容运行时 |
| Go 一方测试 | 145 | 26,398 | 不含第三方 Go 测试 |

三种语言合计约 156,817 行、536 个文件。源量本身不是性能问题，但少数文件承担了大量互不相关的职责：Go `main.go` 4,644 行、eSIM `manager.go` 3,900 行、Rust `registration_coordinator.rs` 2,677 行、`ims_profile.rs` 2,082 行、Swift `CallView.swift` 1,636 行、`BluetoothReaderManager.swift` 1,457 行和 `HomeView.swift` 1,341 行。不要按行数机械拆分；优先看变更冲突、故障归属和测试隔离成本。

本机已有的短信合成测量显示，当前日期解析加分组在 1,000 条时 p95 为 56.585 ms，冻结旧实现为 447.180 ms；分组排序单独约 0.505 ms。保留已有解码优化，不再先建缓存或重写分组。这个结果不包含 SwiftUI 绘制和硬件/IPC 时延。

## 优先候选

| 优先级 | 候选与源码证据 | 预期收益 | 成本 / 风险 | 进入实施的门槛 |
| --- | --- | --- | --- | --- |
| P0 | **已实施：N 待短信转发先取得服务端持久确认，再推进独立游标。** 旧逻辑在非等待任务中暂存转发，通知游标却可先前进；Swift 内存队列另有 5,000 条上限。现在 N 待转发独立读取 changes cursor，按页批量调用 Go enqueue；只有 Go 在加密状态保存成功后返回 HTTP 接收结果，Swift 才持久化该页游标。响应丢失时重放稳定消息 ID，由 Go 的持久去重集拦截重复项。系统通知仍用原通知游标。 | 消除 App 在后端持久接收前退出造成的 N 待转发丢失窗口；失败页留在原位重试。 | 已用隔离 Swift/Go 测试覆盖。本机未连接 provider 或实体读卡器，未验证真实 Telegram/Bark 投递；服务商响应不确定造成的远端重复仍由 Go 的 provider 重试语义决定。 | 已覆盖：接收前失败、服务端接收后响应丢失、重启重放、关闭期间跳过积压、删除后归档正文缺失仍可继续后续短信；正文不进入 UserDefaults。设备短信旧入口不在此改动范围，仍单独评估。 |
| P1 | **多处轮询的总预算与重叠请求。** `DashboardStore` 每 2 秒刷新状态并另以 1 秒查询来电；`SMSStore` 每 3 秒刷新；`MultiStandbyStore` 每 3 秒更新 Profile/变更以便后台通知；模块健康检查约 10 秒；Go N 待状态路径另有 1 秒/5 秒 ticker，短信转发 worker 每 5 秒检查队列。各自有业务理由，但总 CPU、Unix socket 请求和硬件/APDU 调用没有同机统一基线。 | 在不延迟来电、短信发现或 N 待掉线撤销的前提下，减少重复 API 请求、主线程唤醒和后台 CPU。 | 先测约 0.5 工程日；只有过线再做约 0.5–1 工程日的小步调整。将轮询合并得太激进会直接损害及时性。 | App/Rust/Go 前后台各 3×10 分钟；记录每类请求数、耗时、丢弃/合并数、CPU/RSS 与来电/短信延迟。CPU 需下降 ≥20% 且绝对下降 ≥0.5 个百分点；短信刷新 p95 需下降 ≥25% 且 ≥50 ms；不允许新短信发现 p95 恶化超过 5% 或 250 ms（取更严格值）、来电事件 p95 超过 1.5 秒、N 待显式断链撤销 ready 超过 3 秒。 |
| P1 | **N 待短信发送意图只在 Swift 内存中保存一次性 request ID。** `pendingSends` 以 Profile/号码/正文映射到同一 ID，解决进程存活期间的“提交结果未知后重试”；Rust 存储按 `client_request_id` 幂等保存消息。应用重启后 Swift 映射会消失，手动重试会生成新 ID；用户可在历史中看到旧排队记录，但当前发送模型没有暴露该 ID 来无歧义续用。 | 降低提交响应丢失后用户重复发件的风险，同时保留同文案有意再次发送的能力。 | 约 0.5–1 工程日；保存号码/正文会增加隐私风险，不能简单落入明文偏好设置。 | 先写重启/请求响应丢失测试。若确认 UI 无法恢复原始 intent，再将短期 intent journal 存到受保护的本机存储，或由后端提供可恢复的幂等 intent；恢复只允许原 Profile/号码/正文，失败时明确提示结果待确认。测试证明同一 intent 在 App 重启后只生成一条 outbox 记录，而用户再次明确发起的新 intent 仍会产生新消息。 |
| P2 | **APDU 等待路径用 10 ms ticker 轮询锁状态。** `reader_manager.go` 的卡操作准入与 `reader_session_lease.go` 的身份租约会在锁繁忙时反复 `TryLock`。等待有 ctx/deadline，且锁顺序和读卡器独占是正确性边界。 | 读卡器无争用时无影响；高争用时可减少定时唤醒与空转。 | 1–2 工程日，锁通知/公平队列错误可能造成死锁、饥饿或串卡。 | 先统计争用次数、等待分布、Ticker 唤醒量。仅当实际 CPU/唤醒显著，且 p95 等待可改善时，评估带取消语义的 admission channel/notify；维持现有锁顺序，增加取消、热拔插、优先级与并发 Profile 测试。否则不改。 |
| P2 | **按高变更热点拆分大文件，不移动协议语义。** 优先候选是 `backend/cmd/proletarius-macos/main.go` 中的路由与短信归档边界，以及 `HomeView`/`CallView` 中相对独立的视图组成。eSIM 下载/认证文件不列入拆分范围，避免触碰用户明确排除的 `6982`。 | 缩小每次审阅和测试涉及的上下文，减少不同功能改动冲突；不宣称 CPU 加速。 | 每次限定 0.5–1 工程日；跨包搬移和改公共数据模型可能远超收益。 | 同 package / 同 module 做纯移动，不改 JSON、状态机或顺序；拆分前后 API/快照一致，相关测试通过，编译时间不恶化超过 5%。如果仅为了满足单文件行数目标，停止。 |
| P3 | **热点微优化：数组头删、重复编译正则、请求模型复制。** 例如 Swift 转发队列按批次 `removeFirst` 会搬移剩余数组元素，Go 短信 CPMS handler 每次创建同一正则。当前队列有 5,000 上限，合成解码/分组结果也说明常规列表处理已很快。 | 仅在积压或高频调用成为真实 CPU/主线程瓶颈时有收益。 | 常态收益预计低；引入 ring buffer、全局缓存或复杂状态会增加维护面。 | 先用 1,000/5,000 条队列 fixture 与真实请求计数测 p95、分配和 CPU；若绝对收益小于 50 ms 或落在噪声内，不实施。正则只有在确认热调用后才提升为包级变量。 |

## 分阶段实施建议

1. **转发可靠性已完成最小实现。** 增加可控 fake backend，覆盖“服务端已落盘但响应丢失”“接收前失败”、重启恢复与暂停期间游标策略。暂不接 Telegram/Bark 真实账户。
2. **建立统一运行指标，不先合并轮询。** 以无内容日志或计数器分别统计 Swift store 请求、Rust 路由、Go 硬件队列和等待时间；不记录短信正文、Bot token、Bark 密钥或 ICCID。
3. **根据测量结果做一次轮询 A/B。** 保留 1 秒来电保护和 N 待 ready 降级语义；先找出同一刷新周期内重复请求，再逐个 coalesce。未越过收益门槛即停止。
4. **只在改变经常冲突的领域做结构拆分。** 先同 module/file split，再考虑新 package；一轮一个子系统。eSIM 下载/认证和 `6982` 路径保持冻结。
5. **最后审查锁竞争和微分配。** 只为已证明热点动锁或容器结构；结构重构必须以行为等价回归为主，不把代码行数减少记为运行性能。

## 统一验收与停止规则

- 普通性能改造预算不超过 1 工程日；超出先拆小或重新评估。短信持久化/串 Profile 等数据完整性修复可先投入最多 2 工程日做最小修复，再重新评估。
- 一次只改一个假设，固定 2.74 源码快照、Mac、构建配置与 fixture；报告基线和改后 p50/p95、样本数、CPU/RSS、APDU/API 次数及行为差异。
- 任一已确认的短信丢失、串 Profile、重复硬件写、死锁、N 待误报 ready 或呼叫时效回退，立即停止该候选并回退。
- 两轮仍不越过目标、收益小于噪声或维护成本高于收益，记录“停止”，不继续堆缓存或重写。
- 没有真实设备数据时，只报告隔离测试；不以合成测试宣称 VoWiFi、运营商短信或实卡通过。

## 本次结论

N 待转发持久确认与游标提交已按 P0 实施，并通过隔离测试。下一项仍是测量轮询总成本；由于未采集前后台资源与消息延迟数据，本轮没有调整轮询间隔、APDU 等待策略或开展大文件拆分。现有短信解码优化继续保留；发送意图重启恢复仍需单独评估。没有证据过收益门槛的项目暂不实施。

实施边界：本轮只改 N 待转发可靠性与相应定向测试；未运行硬件、未运行长稳、未处理 9eSIM `6982`，未生成 DMG。
