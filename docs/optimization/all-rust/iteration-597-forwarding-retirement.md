## 改动

旧配置退出曾直接消费 runner，并忽略 JoinError。配置请求取消后，后续请求可能无法继续确认旧任务退出；新配置的准入写入也可能脱离请求存活。现在 ServiceState 保留实际 runner、准入写入任务及其配置代次，等待期间取消不会丢失 handle。只有实际任务完成后才能交接；panic、abort 和未确认结果使用固定错误码，主程序的两条退出路径都接收真实 Result，其他清理链继续执行。

新 runner 在真实模式写入成功前不会投递队列。相同配置也必须确认代次仍运行且准入完成，不能掩盖已结束或退出中的任务。构建或回滚失败保留错误和原始加密数据；历史准入/退出失败仍保持可见，不能用一次空配置把关闭报告变成成功。

两个 Rust 短信生产者使用 typed admission。明确关闭保持原来的高水位与不回填规则；配置待确认、退出中或失败则返回错误，不推进 cursor、不重建 baseline。这样不会把暂时不可用解释成用户关闭转发。

## 取舍与后续

本轮是正确性修复，没有新增依赖或更换队列格式。收益是防止配置交接中的漏转发和虚假干净退出；没有以未经测量的性能收益为由扩大改动。原publication/backup故障矩阵的实现未变，595记录仍只属于原切点，没有重新执行或重标其PASS。HTTP固定94中原有2项year1未验证也没有转成通过。

接下来两个已定位的软件缺口分别处理：启动尚未收到GUI配置时，原有`active=None`仍可被当作明确关闭，可能使已有N待转发历史的新消息被高水位跳过；CoreAudio的Stop/Destroy失败仍可能释放回调上下文，部分启动失败也需要保留实际registration并阻止重启。前者需要明确的未确认/已启用/已关闭状态，后者需要按实际系统ACK分阶段退休和真实共享路径测试。均未在本轮冻结源码中宣称已修复。

用户暂缓入站短信，本轮没有访问读卡器、发信、拨号或实网运营商测试。真实Telegram/Bark投递、设备/运营商矩阵、自然租期长稳、原位升级回退和最终交付仍需完成。用户已确认2.80及真实迁移前完整归档不再保留，记录为历史资料不可用，不再反复要求提供路径；旧版等价性未据此补验，也不推定需求已获豁免。

最终清理：构建与测试结束并确认无compiler/target程序、lsof无占用后，仅删除Ruby白名单中的`build/rust-target`和`build/swift-cache`，回收2487635968分配字节（约2.32GiB）。源码、离线依赖、EVS、ARM/离线std、基线、runtime、候选应用和正式DMG未列入删除范围。见`build/reports/iteration-597-cache-cleanup-result.json`。
