## 已确认风险及修正顺序

1. **P0，正在修复：** 读卡器 VoWiFi GUI 先保存原请求，若 POST 在 Rust 持久准入前失败，按请求 ID 查询会得到 `vowifi_request_id_unknown`；旧 UI 将其误称为后台 owner 未结束并长期锁定。修正要求：可证明的准入前拒绝留下持久终态；无回执时以原始 checkpoint 做不重新提交的安全核对；证明不足时继续锁定。需覆盖 POST 丢响应、晚到、重启、账本写失败和当前 owner 并发。
2. **P0 审议优先 / P1 可用性：** `esim_mutation_intent.rs` 的 512 条终态回执上限会永久拒绝后续写卡；未知结果会长期封锁同一 reader/module 范围。设计版本化终态归档及不可重放 tombstone，再提供仅在实体结果人工核对后可用的精确 ID 解除流程；未决意图绝不自动重放。
3. **P0 资源安全：** CCID SELECT 失败后的逻辑通道关闭失败被忽略，后续探测可能继续开通道。将关闭失败标成 cleanup-unknown 并阻止同卡继续操作；故障注入覆盖传输失败与状态字失败。
4. **P1 配置一致性：** 短信转发设置先逐项写 UserDefaults/Keychain，任一中途写失败可能留下新旧混合配置。改为版本化 staging、校验全部凭据后一次发布 active 指针；对每个写入点注入故障并重启验证。
5. **P1 收信完整性：** 转发去重优先使用时间/发件人/内容哈希，两个来源 ID 不同但同毫秒同内容的短信会合并。优先采用稳定归档/实体来源 ID，并保持旧 handoff 的迁移映射，验证重复投递、重启及多号卡隔离。
6. **P1 路径可达性：** App 默认 `-backend=at`，QMI Rust 路由和 transport 的 GUI 可达性、适配机型范围未证明；EF-AD/NAS 读取失败还可能被空值或默认 MNC 长度掩盖。先列明支持设备组成和显式启用路径，错误保留 unknown/degraded，再做实机验收。
7. **P1 代理：** Telegram 系统代理模式须每次提交重新解析，PAC 返回 DIRECT 时不绕过用户要求的代理路径；临时代理失效允许有界重试，提交结果不明不得自动重复。真实 Telegram/Bark 投递仍需单列验收。
8. **P2 性能：** 音频 IOProc 中有锁、分配和数据搬移。先记录 callback p95/p99、队列深度、欠载及并发停止样本；仅有源代码推断不能宣称它导致当前音质问题。
9. **P1 来源门禁：** 已锁定的运营商 YAML 必须在预检中逐文件比对本地 manifest。当前只读检查 1,530 个安装文件均匹配；仍需把该检查纳入自动门禁，并将证书验证的过时说明改为当前实现边界。

安全与持久性缺陷不以性能收益门槛推迟。额外的性能改写沿用原方案阈值：CPU 同时下降至少 20% 且 0.5 个百分点、UI 热路径至少下降 25% 且 50 ms，或 90 天收益至少覆盖两倍工程成本；未达标则记录取舍并停止该优化。启动、API/短信处理和断链恢复的 p95 回退上限按原方案逐项测量，固定机器、Release 产物、设备/Profile 数量、代理及数据规模后比较。

## 长期运行优先的验收

先建立同机同源码的空载、100 条和 1,000 条脱敏消息基线，分别记录 App 与 Rust daemon 的 RSS、文件描述符、线程/任务、持久文件大小、启动与恢复 p50/p95。无设备运行至少 24 小时，并用受控时钟/网络/进程故障脚本覆盖 72 小时等效重试、掉线、代理切换和重启；记录原始样本和事件序列，不能用运行时间替代断言。实机 24/72 小时留在用户排除的物理验收范围内。

硬性断言是：同一外部操作至多提交一次；终态回执不会倒退；消息入站确认前已经耐久归档；未知投递或写卡结果不自动重放；确认释放后没有残余逻辑通道、读卡器租约、VoWiFi session、音频 callback 或子进程；重启后仅从同一持久身份恢复；显式关闭后资源计数返回基线。对内存、句柄和队列深度做趋势回归，增长必须能够由保留策略解释，不能仅凭一次末值通过。任何无法证明资源归属的路径保持隔离并记录为未验收。
