# GitHub-hosted software gates and App candidates

Review and candidate workflows call `.github/workflows/software-gates.yml` at the same revision. All jobs run on GitHub-hosted runners with read-only repository permissions, no inherited secrets and no developer signing certificate. The portable Linux job resolves both committed Rust workspaces using `cargo fetch --locked`, then checks source contracts, formatting and workflow syntax (actionlint v1.7.12). A lockfile mismatch is a failure; do not remove `--locked`.

The macOS Rust job calls `scripts/ci/rust-gates.sh`: both workspaces receive formatting, Clippy and tests. It retains the existing six serial test enumeration check, capsule batch with one test thread, and exact FD isolation. The reviewed existing Clippy warning baseline remains visible; this change does not remove the Clippy gate. The job has a 50-minute limit because the prior complete gate consumed roughly 25 minutes before app or extra Swift coverage.

Offline Swift fixtures run separately in two jobs (25-minute limit): device SMS, network recovery and API request policy use production state models and temporary mocks; forwarding and release initialization share a fault-injection handoff library and require a locked Rust fetch. The latter tests remain offline at runtime and do not use real cards, tokens, Keychain or provider deliveries. App construction has its own 40-minute job after every required test succeeds. Reports include exit codes, elapsed time, source commit and workflow run/attempt; failures upload available evidence and remain failures.

For an explicit latest candidate, select a branch pointing to the desired commit and dispatch `quality.yml` with `build_app=true` and `candidate_sha` equal to that branch's full 40-character SHA, or dispatch `release.yml` with the same `candidate_sha`. A differing ref/SHA is rejected so workflow code and candidate source cannot silently diverge. PR workflow modifications also request an app build, including the actual upload/download smoke check. Draft PRs keep the established portable-only behavior.

The candidate job builds `../dist/Switch.app` once, audits that same app and verifies its ad-hoc signature. It packages the app using tar to retain file permissions and symlinks. `candidate-manifest.json` binds commit, Git tree, source digest, run URL/attempt, actual toolchain/SDK/host, per-file App inventory and report checksums to the archive SHA-256. `SHA256SUMS` covers the archive and manifest. The archive is named `Switch-<version>-candidate-<full SHA>-macOS27-arm64.app.tar.gz`; VERSION is unchanged and this is not the original v3.51 release.

The workflow uploads the candidate, downloads that actual artifact, verifies archive bytes, all file contents, executable modes, symlinks and report hashes, then uploads an `upload-roundtrip` report separately. A successful candidate workflow requires this real roundtrip. Both artifacts and test reports have seven-day retention and attempt-specific names. Download the tar archive and extract it to preserve executable bits; do not upload a bare `.app`.

This produces no DMG, does not invoke `release.sh`, and cannot manufacture `product-final` acceptance. The manifest explicitly records incomplete product/device acceptance, ad-hoc signing and no notarization. macOS 26 GitHub runners and a macOS 27 deployment target do not demonstrate macOS 27 runtime compatibility, carrier registration, real SMS/calls or long-running device stability. Those remain separate acceptance work.


## Explicit reviewed preparation

The already registered `quality.yml` supports `workflow_dispatch` with `prepare_reviewed=true` and an exact `candidate_sha`, only on `automation/cloud-four-batches`. This path skips software/build gates and calls the reusable reviewed preparation workflow. Only this job receives contents:write; no PR or tag can invoke it. The regular gates never refresh their own review evidence.

The root reviewer commits `docs/ci/reviewed-prepare-authorization.json` as the sole change on top of `reviewed_source_commit`. Schema version 1 contains `baseline_commit`, `reviewed_source_commit`, `reviewed_files` (path and reviewed Git blob SHA for every changed Rust/Swift file), `scopes` (file, nullable function, old_sha256 and concrete review_note), and `functional_acceptance_awarded:false`. The dispatch SHA includes this authorization. The runner validates old metadata against baseline, applies rustfmt only within allowed source files without changing normalized tokens, updates only explicitly approved changed fingerprints, regenerates the contract census with the existing checker and runs source/fmt checks. No scope can be added or silently blessed.

The preparation commit is a direct child of the requested SHA. An exact Git push lease advances only the allowed branch if its head still equals that SHA; a concurrent change aborts rather than being overwritten. The report preserves authorization blob, old/new fingerprints, changed files and prepared commit. The root explicitly starts the ordinary quality run at the new SHA. This is source review maintenance, not product acceptance.

For GitHub's "re-run failed jobs", successful gates from an earlier attempt of the same run and exact source SHA remain usable. The candidate downloads original gate artifacts across attempts, ignores copied reports in previous candidate artifacts, and selects each gate's latest record. A latest failed record is never replaced with an earlier pass. The manifest records source artifact IDs/names and each gate's original attempt.
